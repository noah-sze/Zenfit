# Zenfit 產品規格與架構白皮書 (Product Spec & Architecture)

## 1. 產品定位與核心使命 (Product Definition & Mission)
- **產品定義**：
  Zenfit 是一款純客戶端、本地優先（Local-First）且支援離線運行的「個人飲食與健身記錄 PWA 應用程式」。
- **核心使命**：
  為認真自律的健身愛好者與自我量化者，提供一把極致高效、無干擾、零延遲、極簡高質感的數據測量儀。
- **目標體驗**：
  - **極速記錄**：操作流程無摩擦，每一次輸入皆在毫秒級內響應。
  - **數據透明**：數據 100% 歸使用者所有，所有計算公式與關聯公開透明。
  - **無感離線**：無論在地下室健身房或飛行模式下，功能均完備可用。

## 2. 核心產品哲學與設計邊界 (Product Philosophy & Strict Boundaries)
- **測量儀與客觀鏡子**：
  軟體不是說教的教練，而是一把極致鋒利、精準、冷靜的「測量儀與客觀鏡子」。
- **純粹事實，拒絕批判**：
  **只呈現客觀事實，不做主觀批判；只計算數學關聯，不給行為指令。**
- **嚴禁說教與行為干涉 (Zero Preachiness & Non-Prescriptive)**：
  - **嚴禁行為干涉**：絕對禁止在產品各處主動指示使用者「你該吃什麼」、「你少吃了」、「你吃超標了」、「你該做幾組」、「你今天退步了」或「你該減量了」。
  - **拒絕焦慮製造**：不設置具有羞辱感、道德說教或焦慮感的紅色超標警報、警告卡片或批判性狀態。
  - **決策權 100% 歸還使用者**：所有數據呈現均作為純粹的中立事實，供使用者自行觀察、推演與決策。軟體只專注於**「極速且無摩擦的記錄」**與**「高維度且精密的數據呈現」**。
- **非目標範疇 (Non-Goals / 產品不做什麼)**：
  - 不做社交社群平台，不提供動態分享或心靈雞湯。
  - 不做黑盒化、未經科學驗證的所謂「AI 智能評分」或行為打分。
  - 不設置強制性打卡或斷簽懲罰機制。

## 3. 核心功能範疇 (Functional Scope)
### 3.1 飲食與營養追蹤 (Nutrition & Macro Tracking)
- **精確熱量與宏量素記錄**：支援食物熱量（Calories）、蛋白質（Protein）、碳水化合物（Carbs）、脂肪（Fat）的快速錄入與份量計算。
- **供能比與客觀對比**：提供客觀宏量營養素供能比計算（P/C/F 比例），使用者可自訂預期參考值，介面僅呈現客觀差值與進度，不做批判標籤。
- **趨勢與滾動平均**：提供 7 天 / 30 天攝入熱量滾動平均（Rolling Average），過濾日常進食波動。
- **原子食材與複合菜餚分層架構 (Atomic Ingredients vs Composite Recipes)**：
  - 單品食材為純粹客觀的物理常數（生重/客觀營養標籤），複合菜餚為多項食材與烹調用油的引用聚合。
  - 徹底摒棄黑盒化「成品菜估算」，引導使用者建立以克數 (`g`) 為基準的物理秤重習慣，從源頭杜絕隱藏用油誤差。

### 3.2 肌力與訓練記錄 (Strength & Workout Logging)
- **極簡課表與動作庫**：依據肌肉群分類的自訂動作庫，支援快速選取與歷史記錄帶入。
- **精密組數與強度計量**：
  - 記錄重量（Weight）、次數（Reps）、RPE（自覺自竭程度）與熱身組/正式組屬性。
  - 自動計算單次動作的預估極限力量（e1RM，例如採用 Brzycki / Epley 公式）。
  - 自動統計每週有效訓練組數分佈（Weekly Effective Sets per Muscle Group）。

### 3.3 體重與身體指標 (Weight & Body Metrics)
- **抗噪趨勢分析**：採用數學平滑算法（如指數移動平均 EMA），消除人體水分與胃腸道滯留造成的短期體重波動，呈現真實生理趨勢。
- **能量平衡推算**：依據真實體重平滑變化斜率與長期飲食攝入數據，計算實際客觀能量盈虧。

## 4. 系統與數據架構 (System & Data Architecture)
### 4.1 本地優先架構 (Local-First Architecture)
- **資料庫引擎**：全面採用瀏覽器端本地 IndexedDB 作為唯一資料真理源，底層基於 Dexie.js 進行強型別數據管理。
- **四重資料安全防線與 Schema 遷移紀律 (Zero Data Loss & Schema Migration Discipline)**：
  1. **嚴格版本號遞增與升級腳本**：IndexedDB 結構變更必須嚴格遞增 Dexie `.version(n)`，並強制編寫相應的 `.upgrade(async tx => ...)` 遷移腳本，保證使用者既有資料平滑過渡。
  2. **絕對禁止生產環境破壞性清庫**：嚴禁在生產環境中執行未經備份的刪表 (`drop table`) 或清空資料庫操作 (`db.delete()`)。
  3. **存儲持久化保障 (Storage Persistence API)**：在應用程式初始化時主動呼叫 `navigator.storage.persist()`，請求瀏覽器授予持久化儲存權限，徹底杜絕設備磁碟空間吃緊時 IndexedDB 被靜態逐出的風險。
  4. **版本遷移前數據快照防護**：重大結構變更前必須執行數據完整性檢驗與暫存快照防護，若升級過程發生異常必須安全回滾或終止，不得損毀原始數據。
- **零網路依賴**：所有資料建立、讀取、更新、刪除（CRUD）與複雜統計運算均在客戶端即時執行，即使完全斷網也能毫無阻礙地使用全部功能。

### 4.2 漸進式 Web 應用 (PWA & Offline Capabilities)
- **服務工作線程 (Service Worker)**：透過 Workbox 與 Vite PWA 外掛實現離線靜態資源完全快取（Cache-First 策略）。
- **原生級安裝體驗**：符合 PWA 規範，提供標準 Web App Manifest，支援在 iOS、Android、macOS 及 Windows 上一鍵安裝至桌面或主畫面。

### 4.3 數據同步抽象層與端到端加密 (Sync Provider & E2EE)
- **同步介面抽象 (Sync Interface)**：將資料同步抽象為標準介面（`SyncProvider`），使核心業務代碼與具體雲端儲存實現徹底解耦。
- **端到端加密 (E2EE)**：雲端同步傳輸與備份時，資料必須在客戶端透過使用者金鑰完成加密（如 AES-GCM / Web Crypto API），雲端儲存節點僅儲存密文，實現零知識（Zero-Knowledge）架構，確保隱私絕對安全。

## 5. 工程架構與代碼組織準則 (Engineering Principles)
- **職責分離 (Separation of Concerns)**：
  - `src/components/`：純 UI 渲染與呈現層，不得包含複雜業務邏輯與非視圖計算。
  - `src/hooks/`：所有狀態管理、資料庫查詢封裝、事件處理與運算邏輯集中於自定義 Hooks。
  - `src/services/`：外部 API、資料庫連線、加解密與資料同步等底層服務。
  - `src/store/`：全域客戶端狀態（如主題、當前日期等輕量狀態）。
  - `src/utils/`：純函數數學公式、日期格式化與輔助工具。
  - `src/types/`：領域模型與資料庫實體的 TypeScript 嚴格定義。
- **SOLID 原則與代碼簡潔性**：嚴禁過度設計，但必須為未來功能演進保留標準介面擴展性。
